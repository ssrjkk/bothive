## 1. Миссия и принципы

**Продукт:** автоотклики на вакансии, кабинет соискателя, Telegram-бот.

| #   | Принцип                                        | Что это значит на практике                                                                     |
| --- | ---------------------------------------------- | ---------------------------------------------------------------------------------------------- |
| P1  | **Правда о происхождении**                     | Каждый факт имеет `origin`: `real`, `simulated`, `user`, `ai`. Лучше отсутствие, чем неправда. |
| P2  | **Необратимое — только с человеком**           | Отклик уходит после тапа или по правилу, которое человек сам утвердил.                         |
| P3  | **Идемпотентность**                            | Любое внешнее действие безопасно повторить: второй раз эффекта нет.                            |
| P4  | **Минимум данных**                             | Секреты не в открытом виде, не в логах, не в сообщениях бота.                                  |
| P5  | **Проверка, которая не падает, — не проверка** | Поведенческие тесты вместо сканирования исходников. Каждый тест обязан уметь упасть.           |

## 5. Дорожная карта

Порядок важен: сначала правда и необратимость, потом бот, потом рост.

### Фаза 1 — Правда и безопасность

- ✅ Колонка `origin` (`real | simulated | user | ai`) в откликах; миграция
  вперёд и идемпотентная (`migrateApplicationsOrigin`: дефолт `user`,
  backfill hh→`real`). Таблица `events` создана сразу с origin-CHECK
  (писателей пока нет — появятся в Фазе 3).
- ✅ Поле `mode` у пользователя: `demo | live`. `live` — только после подключения hh
  и явного согласия. Колонка `mode TEXT NOT NULL DEFAULT 'demo' CHECK (mode IN
('demo','live'))` (`db.ts`), миграция вперёд и идемпотентная
  (`migrateUserMode`), роут `/api/mode` (GET/POST). Подключение hh само по себе
  live не включает; отключение hh гасит live в demo (`clearHhConnection`).
  Проверка «подключён ли hh» вынесена в одно место, `isHhConnected`, иначе
  `/api/hh/status` и `/api/mode` разошлись бы. 11 тестов, `user-mode.test.ts`.
- ✅ Баннер демо-режима в layout кабинета (`DemoBanner`, серверный компонент,
  рендерится на сервере — человек не успевает увидеть живые цифры без
  пометки). В `live` не рендерится ничего: постоянная плашка обесценила бы
  настоящие данные. Переключатель режима в настройках (`ModeSwitch`) — до
  него роут `/api/mode` был недостижим из интерфейса. Кнопка live не
  предлагается без подключённого hh, причина отказа сервера показывается
  дословно. 9 тестов: `demo-banner`, `mode-switch` (jsdom) и
  `demo-mode-browser` (Chromium по живой сборке).
- ❗ Пометка в боте и на воронке — не сделано. Баннер есть только в кабинете.
- В `demo` симуляция работает и ничего наружу не уходит. В `live` симуляции нет.
- `ensureLocalSeeded()` не должен наполнять каталог на проде без явного флага.
- Токены hh шифруются в БД, ключ из окружения.

**Готово когда:** I5, I6 покрыты тестами; в `live` нет ни одной симулированной строки.

### Фаза 2 — Необратимость

```sql
CREATE UNIQUE INDEX IF NOT EXISTS ux_applications_once
  ON applications(user_id, source, external_vacancy_id);
CREATE TABLE IF NOT EXISTS scheduler_lock (
  name TEXT PRIMARY KEY, holder TEXT NOT NULL, expires_at INTEGER NOT NULL
);
```

- Порядок: `INSERT pending` → внешний запрос → `UPDATE sent` или `failed`.
- Сверка зависших `pending` со списком откликов на стороне hh; слепых повторов нет.
- Блокировка планировщика в БД плюс защита от наложения тиков внутри интервала.
- Рубильники: `AUTOAPPLY_ENABLED`, `AUTOAPPLY_DRY_RUN`, пауза пользователя.
- Дневной лимит считается запросом к БД, а не счётчиком в памяти.
- Журнал `apply_events` только для добавления.

**Готово когда:** I4, I8 покрыты; тест «`fetch` успешен, следующий `UPDATE` упал» не даёт второго отклика.

### Фаза 3 — Фундамент бота

```sql
CREATE TABLE events (id INTEGER PRIMARY KEY, user_id INTEGER NOT NULL,
  kind TEXT NOT NULL, origin TEXT NOT NULL CHECK (origin IN ('real','simulated','user')),
  entity_type TEXT, entity_id INTEGER, payload TEXT NOT NULL,
  dedupe_key TEXT UNIQUE, created_at INTEGER NOT NULL);
CREATE TABLE outbox (id INTEGER PRIMARY KEY, chat_id INTEGER NOT NULL,
  event_id INTEGER REFERENCES events(id), priority INTEGER NOT NULL,
  body TEXT NOT NULL, markup TEXT,
  state TEXT NOT NULL DEFAULT 'pending', attempts INTEGER NOT NULL DEFAULT 0,
  next_try_at INTEGER NOT NULL, tg_message_id INTEGER);
CREATE TABLE tg_updates (update_id INTEGER PRIMARY KEY, seen_at INTEGER NOT NULL);
```

- Webhook: секрет за постоянное время → запись `update_id` (конфликт = повтор) → 200 сразу → воркер.
- Воркер outbox: приоритеты, токен-бакет, 429 (`retry_after`) и 403 (чат гасится).
- Команды латиницей через `setMyCommands`; русские слова как запасной вариант.
- Данные кнопки: `v1|act|entity_id|card_ver`; сервер проверяет владельца и версию.
- Привязка аккаунта: только личный чат, ограничение попыток, уведомление в кабинете.

**Готово когда:** I11 покрыт; фейковый `api.telegram.org` подтверждает дубль апдейта, чужую кнопку, устаревшую карточку, 403 и 429.

### Фаза 4 — Живой поток

- События только `origin = 'real'`, дедупликация по `dedupe_key`.
- P0 приглашение (сразу, с кнопками, пробивает тихие часы); P1 смена этапа; P2 «просмотрено» в дайджест; отказы пачкой раз в день.
- Тихие часы по IANA-поясу. Утренний дайджест опционально.

**Готово когда:** p95 «событие → сообщение» меньше минуты на фейковом API; P0 переживает падение воркера.

### Фаза 5 — Триаж и доверие

- Карточка вакансии: объяснение совпадения, кнопки «Откликнуться / Пропустить / Скрыть компанию».
- Причины пропуска превращаются в явные правила фильтров; правило видно и удаляется.
- Отправка с отменой: очередь 5–10 минут, «Отменить» и «Править письмо».
- **Проверка утверждений:** навыки, годы, компании и цифры из письма сверяются с резюме; неподтверждённое блокирует отправку.
- Модель предлагает черновик, но не вызывает «отправить» (I7).

**Готово когда:** I7 покрыт; письмо с непроверенным фактом не доходит до очереди.

### Фаза 6 — Интервью

- Сущность `interview`, дата разбирается из текста и подтверждается кнопками.
- `.ics`, напоминания за сутки, час и 15 минут (UTC библиотекой, знающей DST).
- Сводка накануне, разбор после встречи, follow-up через 5 дней тишины.
- Черновики ответов рекрутёру; отправка только по тапу.

### Фаза 7 — Рост

- ✅ **A/B-варианты одного резюме** — легальная часть совета «тестируй
  гипотезы на нескольких версиях». Один человек, одно резюме в нескольких
  редакциях; рекрутер видит одного кандидата. Колонки `variant_group` /
  `variant_label` в `resumes` (`migrateResumeVariants`), домен
  `resume-variants.ts`, роут `POST /api/resumes/[id]/variants`. 9 тестов.
  - **Соединение с откликами идёт по `hh_id`, а не по `resumes.id`** —
    `applications.resume_id` объявлен TEXT и хранит идентификатор резюме на
    hh (`migrateApplicationsResumeId`). Вариант без `hh_id` не может иметь
    откликов и показывается нулём, а не выбрасывается.
  - **Победитель не назначается на малой выборке.** Меньше
    `MIN_SAMPLE_PER_VARIANT` (5) откликов на вариант — `leader: null` и
    объяснение, чего не хватает. Карта запрещает выводы на малой выборке.
  - **Демо-симуляция не участвует** в подсчёте (`origin IN ('real','user')`),
    иначе победителя выбирал бы планировщик.
  - ✅ Экран в кабинете: `VariantPanel` (создание варианта + честное сравнение),
    `GET /api/resumes/[id]/variants`. Свою ошибку поймал на живой проверке:
    кнопка «Создать вариант» рендерилась только при `variants.length > 0`, то
    есть **первый** вариант создать было некем, хотя панель об этом просила.
  - ❗ Не сделано: загрузка варианта на hh, выбор варианта в автоотклике.
- ❗ **НЕ делается: мультиаккаунт и подмена личности.** Совет из ролика
  «создай 10 аккаунтов, новый телефон, почту, Telegram, дату рождения, чтобы
  обойти дедупликацию hh» в продукт не встраивается. Причины конкретные: это
  спам живому рекрутеру (десять одинаковых «кандидатов» вместо одного
  приглашения), hh.ru банит за одинаковые ФИО и телефоны, риск основного
  аккаунта, и прямое противоречие P1 и разделу 9. Если ssrjkk всё же захочет —
  принимается осознанно и отдельной задачей, не по умолчанию.
- ❗ **Деплой: `github.io` не подходит.** GitHub Pages раздаёт только статику,
  у приложения 38 роутов, SQLite и планировщик. Нужен сервер с диском.
  Готовый стек (Caddy с авто-TLS, бэкап с проверкой восстановления) лежит в
  `docker-compose.prod.yml` и `scripts/backup.mjs`; разворачивается одной
  командой `docker compose -f docker-compose.prod.yml up -d --build`.
  - ❗ **`ezoffer.ru` уже занят** (замерено 17.10.2026: отдаёт парковочную
    страницу регистратора, `Server: openresty`). Строка `SITE_URL=https://ezoffer.ru`
    в `docker-compose.yml` указывает на чужой домен и должна быть заменена.
    `ezoffer.com` не резолвится. Регистрация домена и DNS — только через
    аккаунт ssrjkk, агент это сделать не может.

- Пересылка ссылки или текста вакансии → разбор по схеме → подтверждение → учёт.
- Inline-режим. Mini App с валидацией `initData` по HMAC и свежести `auth_date`.
- Недельный разбор только по `origin = 'real'`.

## 6. Протокол работы агента

1. **Читай перед правкой:** сам файл, его тест и места вызова.
2. **План из 3–5 строк**, потом правки. Одна задача — один коммит.
3. **Для инварианта сначала тест.** Убедись, что он краснеет на сломанном коде, потом чини.
4. **Не расширяй задачу.** Найденное сбоку — в «Находки», молча не чини.
5. **Миграции БД:** только вперёд, идемпотентные, проверенные на пустой и на заполненной базе.
6. **Ворота перед «готово»:** `tsc`, lint, все тесты, `git status` чист.
7. **Нельзя без явного разрешения:** `git push`, удаление данных или файлов вне задачи, мажорные обновления зависимостей, внешние сетевые вызовы, включение реальных отправок.
8. **Не уверен — остановись и задай один вопрос.**

## 7. Стратегия тестов

- unit домена (скоринг, парсеры, лимиты);
- **поведенческие тесты роутов** по всем 37: нет сессии, чужой id, битый id, битое тело;
- фейковые внешние API (hh, Telegram, SMTP) на подмене `fetch` со счётчиком вызовов;
- Chromium для UI и баннеров;
- инварианты живого каталога.

**Уроки прошлых прогонов:**

1. Считать код, а не регулярки: страница не «невыщитана», если в ней `parseParamId`, проверка владения и `sanitizeExternalUrl`.
2. Не искать вызов «где угодно», включая строку импорта.
3. Считать обработчики против вызовов, а не «хотя бы один в файле».
4. Утверждение, которое нельзя сломать, удалять, а не оставлять.
5. Непокрытое записывать прямо в файле теста.
6. Поведенческий тест бьёт по **работающей сборке**: правка исходников его не роняет, пока сервер не пересобран.
7. **404 от устаревшей сборки проходит как «хороший 4xx».** Обход берёт список роутов из файловой системы, а сервер отвечает 404 на только что добавленный путь — и тест считает это успехом. Новый роут получает бесплатный зелёный билет, ни разу не выполнившись. Замерено 16.10.2026 на `/api/mode`: сервер жил 2 часа, пути не знал, тесты были зелёные. Роут, добавленный в обход, надо проверять прямым вызовом обработчика либо пересборкой сервера.

## 11. Находки (записаны, молча не чинились)

1. **`tests/freelance-sources.test.ts:119` — тест бьёт по живому фиду fl.ru и
   потому мигает.** Три прогона 16.10.2026: сеть недоступна → `skip`, сеть есть →
   падает. Упал на заказе «Копирайтер для переработки текстов сайта: инженерные
   системы, B2B, умный дом»: `detectDirection` вернул `other`, а тест требует, чтобы
   у всего, что попало в ленту, было направление. Файл сам признаёт эту историю
   (`:132-143`): проверку уже чинили погоней за лентой добавлением слов. **Не в
   фазе `mode`:** общих файлов с этой задачей нет. Варианты — фиксированная
   репрезентативная выборка вместо живой ленты, либо явное «проверка каталога на
   живой ленте не входит в зелёные ворота». Решение за владельцем, ворота мигают.
2. **Поведенческие тесты роутов проверяют ту сборку, что запущена, а не
   рабочее дерево.** Найдено на `/api/mode`: сервер жил два часа, пути не знал,
   отвечал 404, а тест считал это «правильным 4xx». Подробности — урок 7
   раздела 7. Сервер пересобран, `/api/mode` теперь проверяется по-настоящему,
   но правило остаётся: **после правки исходников — `npm run build` и перезапуск,
   иначе зелёный цвет поведенческих тестов ничего не значит.**
3. **`tsc` ловит рассинхрон типа `User` только в тестах.** Добавление `mode` в
   `User` уронило две локальные копии фабрики (`telegram-bot`, `telegram-commands`) —
   они дублируют форму `User` вместо `satisfies User`. Стоит подумать про одну
   общую фабрику, иначе каждое новое поле `User` ломает тесты в нескольких местах.
4. **Проверка «показана ли ошибка» по всему тексту страницы ложноположительна.**
   Нашлось на себе: `assert.match(text, /hh\.ru/)` проходило всегда, потому что
   «статусы приходят только от hh.ru» есть в статическом пояснении панели.
   При сломанной обработке отказа (`!res.ok && false`) тест оставался зелёным.
   Правильно — проверять конкретную живую область `[role="alert"]`.
5. **Проверка «не наследуется hh_id» на резюме без hh_id не может упасть.**
   Копирование `NULL` даёт `NULL`, и утверждение «hh_id не унаследован» зеленеет
   на сломанном коде. Предусловие обязано быть явным: сначала выдать исходнику
   `hh_id`, потом клонировать.
6. **Полный прогон встаёт, если сервер на `BASE` не поднят.** `npm test` без
   работающего сервера не просто шумит — он может не закончиться (поведенческие
   тесты плюс сетевой фид). Перед прогоном: `npm run build` → старт сервера →
   тест. Сервер, поднятый через `Start-Process`, умирает вместе с сессией
   PowerShell — поднимать фоновым процессом.
7. ~~Браузерные тесты привязаны к лимиту запросов.~~ **Исправлено 17.10.2026.**
   `proxy.ts` режет страницы 30 в минуту и `/api` — 60. `npm test` делал сотни
   запросов подряд, и к концу прогона квота исчерпана: падала ПОСЛЕДНЯЯ
   страница, а повторный запуск — вход (login получал 429). Лимит **не
   поднимали** — он прав. Починен порядок тестов: `tests/helpers/rate-limit-retry.ts`
   ждёт своё окно (Retry-After, иначе 2 с) и повторяет попытку. Повторяется
   **только 429** — на любой другой код тест падает сам, иначе retry стал бы
   глотком на настоящие ошибки. После правки полный прогон: 814 тестов,
   813 прошло, 1 упало (живой фид).

## 12. Автоотклики на hh.ru: что осталось за ssrjkk

Код готов и проверен: `POST api.hh.ru/negotiations` (`vacancies/hh.ts:221`),
OAuth и refresh (`hh-oauth.ts`), планировщик и паузы (`autoapply.ts`).
Блокирует одно — OAuth-приложение на dev.hh.ru не создано. Ошибка
«Не настроено на сервере» означает ровно это: `hhConfigured()` вернул false.

Ключи может выдать только аккаунт на dev.hh.ru, поэтому их нельзя ни
сгенерировать, ни обойти — это не вопрос разрешения, а физический факт.

**Нужно сделать (5 минут на dev.hh.ru → «Мои приложения»):**

1. Создать приложение (или взять существующее).
2. Redirect URI: `https://ezoffer.ru/api/hh/callback` — посимвольно как в
   `HH_REDIRECT_URI`, иначе hh отвергнет callback.
3. Права: «Отклики» (negotiations), «Чтение откликов», «Чтение вакансий»,
   «Резюме».
4. Вписать в `.env`: `HH_CLIENT_ID`, `HH_CLIENT_SECRET`, `HH_REDIRECT_URI`.
5. Перезапустить и подключить аккаунт в кабинете.

**Два рубильника, которые надо осознанно выставить при включении:**

- `AUTOAPPLY_DAILY_CAP=0` означает **«без глобального потолка»**, а не «выключено»
  (`config.ts:26`). Пока так — ключи плюс активный поиск дают реальные отклики
  живым рекрутёрам каждые 45–180 секунд. Ставится осмысленное число.
- Письма пишет модель, а проверка утверждений (Фаза 5) не сделана. Пока её нет,
  модель может написать в письмо навыки, годы или компании, которых нет в
  резюме. Поэтому автоотклики включаются после Фазы 5.
